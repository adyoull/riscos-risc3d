# RISC3D 0.12

Contexts that share objects, and a current context per thread, for
WebKit 2.52. Its drawing library, Skia, draws with OpenGL ES in several
threads at once, each with its own context, all sharing one set of
textures and buffers.

On native RISC OS, riscos-mesa does this through its own GPU driver. On
RISC OS on Linux it needs RISC3D 0.12.

## What's in it

- **RISC3D-0.06-1.zip:** `!RISC3D`, for `!Boot.Resources`. It is also the
  PackMan package RISC3D.
  - **The RISC3D module 0.06:** `RISC3D_Open` can make a context that
    shares another's objects (r0 bit 0, r1 = the other context). Drivers
    that can share register with flags bit 2. `RISC3D_Info`'s r4 bit 2 says
    whether they can now.
  - In `GPU`:
    - **Linux3D 0.06:** RISC OS on Linux. Opens a shared context in the
      other context's Linux process.
    - **V3DRender 0.16:** Raspberry Pi 4, 400 and CM4 (unchanged).
- **riscos-risc3d 0.23-1:** RISC OS on Linux's side, rol-3d 0.20. Each
  context's process can take more contexts, as threads sharing its
  objects.
- **RISC3D-client-0.12.tgz:** the client library riscos-mesa builds in.
  - `r3d_create_shared (api, major, minor, share)` and `r3d_can_share ()`.
  - Each thread has its own current context. A program with one thread
    costs no more than before.
  - Texture, buffer and list names and sync objects are one set for
    contexts that share.

Everything works as before with the old parts mixed in. Sharing needs all
three new ones; otherwise `r3d_can_share` is 0 and programs draw in
software.

## Ordering between contexts

As in GL, one context sees another's work after `glFinish` in the first,
or after a fence: `glFenceSync` and `glFlush` in the first, then
`glWaitSync` or `glClientWaitSync` in the second.

## Tested

On the build machine (Mesa's llvmpipe): `sharetest`, ten runs, and every
earlier test unchanged. The Pi 4 under ROL: kit 38.
